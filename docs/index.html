Core Architecture & Design Decisions

Key engineering patterns that keep the system correct under pressure.

💰 Whole Cents (BIGINT)
Never store currency as float or double. IEEE 754 binary floating-point representation causes roundoff inaccuracies (e.g. 0.1 + 0.2 = 0.30000000000000004). Whole cents in BIGINT eliminate all fractional drift.
⚖️ Double-Entry Bookkeeping
Every transfer generates two mirrored ledger entries: a debit (-amount) on the sender and a credit (+amount) on the recipient. Summing all entries across time strictly equals zero, providing a tamper-proof audit trail.
🔒 Pessimistic Row Locking
Uses SELECT ... FOR UPDATE at the database engine level. Unlike optimistic locking which causes retry storms on contested accounts, pessimistic locking queues transactions in serializable order.
🔁 Deadlock-Free Lock Hierarchy
To prevent deadlocks when transfers cross paths (A → B vs B → A), locks are always acquired in ascending account ID order: min(id1, id2) before max(id1, id2). Deadlock cycles are mathematically impossible.
🔑 Database Unique Idempotency
Enforced by PostgreSQL's UNIQUE constraint on idempotency_key. Application checks alone fail under sub-millisecond races; the database index acts as the ultimate gatekeeper, turning collisions into cached replays.
🧪 Real Containerized Verification
Tested against real PostgreSQL via Docker locally and in GitHub Actions CI. In-memory databases like H2 mask concurrency anomalies; real PostgreSQL tests prove actual row locking behavior.

REST API Specification

Simple, clean HTTP contract with strict headers and JSON payloads.

POST /accounts — Create Account
Creates a new bank account with an initial balance in whole cents.
POST /accounts Content-Type: application/json { "owner": "Alice", "initialBalanceCents": 10000 } Response (201 Created): { "id": 1, "owner": "Alice", "balanceCents": 10000 }
POST /transfers — Execute Idempotent Transfer
Moves funds between accounts. Requires the Idempotency-Key HTTP header.

Interview Deep-Dive & Master Answers

Key technical topics you can speak fluently about in software engineering interviews.

1. What is a "Lost Update" anomaly and how did you reproduce it? ▾
A lost update occurs when two concurrent transactions read the same initial state (e.g., balance = $50), each calculates a new balance in memory ($49), and both write it back to the database. The second write completely overwrites and erases the first transaction's debit. In our automated test firing 50 concurrent $1 withdrawals without locking, Alice ended up with $44 instead of $0—$44 of withdrawals vanished into thin air!
2. Why does sorting Account IDs prevent deadlocks? ▾
Deadlocks occur when two transactions form a circular dependency: Transaction 1 locks Account A and waits for Account B, while Transaction 2 locks Account B and waits for Account A. By enforcing a strict global lock hierarchy—always locking min(id1, id2) before max(id1, id2)—both transactions must compete for the exact same lower-numbered account first. One acquires it while the other queues, making circular waits impossible.
3. Why isn't a Java "if exists" check enough for idempotency? ▾
Due to race conditions: if a user double-clicks submit or an automated retry hits within 2 milliseconds, both threads check existsByIdempotencyKey() simultaneously before either has written to the database. Both see "false", both execute the transfer, and the user is charged twice. Enforcing a UNIQUE constraint at the database index level guarantees atomicity; the database rejects the second insert, rolls back its transaction, and allows us to return the original receipt.
4. Why use Pessimistic Locking instead of Optimistic Locking? ▾
Optimistic locking (@Version) works well for low-contention scenarios (like editing a blog post), but on high-volume financial accounts (like a popular merchant or payroll account), dozens of threads attempt to modify the same row simultaneously. With optimistic locking, 49 out of 50 requests fail with optimistic lock exceptions and must retry in expensive loops. Pessimistic locking (SELECT ... FOR UPDATE) puts transactions into an orderly database queue, maximizing throughput without wasting CPU.
